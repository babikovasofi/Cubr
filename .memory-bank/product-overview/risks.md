# Cubr — Риски и трудности

> Проблемы и стратегия. Технические решения — [tech-details/solutions.md](../tech-details/solutions.md).
> Отсортировано по опасности: сверху то, что может убить проект.

---

## R1. Зрение кубика — главный риск проекта 🔴

**В чём проблема:**
- Белый и жёлтый сливаются при тёплом освещении
- Красный и оранжевый почти неразличимы — классическая боль всех cube-scanner'ов
- Stickerless-кубики без чёрных границ между наклейками сложнее сегментировать
- Блики от ламп «съедают» цвет наклейки
- У всех разные кубики (палитры, потёртость) и разное освещение

**Митигация:**
1. **Профиль кубика + быстрая подстройка одной гранью каждую сессию** (утв. фича, уточняет
   исходную «калибровку каждый раз» — см. [feature-cube-profiles](feature-cube-profiles.md)):
   игрок регистрирует кубик один раз (6 граней → 6 Lab-эталонов), а перед каждой игрой показывает
   ОДНУ грань собранного кубика → система вычисляет сдвиг освещения и применяет ко всем 6 эталонам
   (~3 сек вместо 15–20). Если после сдвига попарные ΔE между эталонами < порога различимости →
   полная перекалибровка (6 граней). Классификация всегда относительно эталонов профиля, не
   абсолютных HSV-порогов. Честность сохранена: система всё равно видит собранный кубик в начале
   каждой игры (подтверждение честного старта). Порядок ритуала: **собранный кубик показывается
   ПЕРВЫМ, до скрамбла** (Часть A той же спеки).
2. **Классификация относительная, не абсолютная**: на кубике всегда ровно 9 наклеек каждого цвета — кластеризация 54 наклеек на 6 групп по 9 с этим жёстким ограничением сильно повышает точность.
3. Ручная калибровка в настройках — запасной вариант.
4. UX-фолбэк: если грань не читается 3 раза — подсказки про свет + возможность подтвердить цвет вручную (только вне соревновательных проверок).
5. **Этап 0 (прототип зрения) — первым в плане.** Если не взлетит — пересматривать проект до написания остального кода.

## R2. Детект «руки на столе» 🔴

**В чём проблема:** MediaPipe даёт landmarks рук, но не глубину — «рука лежит на столе» и «рука висит над столом» в лоб неразличимы. Плюс дребезг: рука мелькнула в кадре → ложный старт/стоп таймера.

**Митигация:**
- Зона на экране («положи руки сюда»): руки должны быть внутри зоны и **неподвижны** N миллисекунд
- Конечный автомат состояний с задержками подтверждения (debounce) на каждый переход: нет рук → руки в зоне → руки неподвижны → подтверждено
- Тюнить пороги на реальных людях на Этапе 0–1

## R3. Точность таймера и честность таймингов 🟠

**В чём проблема:** спидкуберы меряют сотые секунды, а зрение работает покадрово (30 fps ≈ шаг 33 мс). Плюс клиентскому времени нельзя доверять — его можно подделать.

**Митигация:**
- Фиксировать старт/стоп по кадру, честно указать точность в правилах (например ±0.05 с — одинаково для обоих игроков в дуэли, поэтому справедливо)
- Сервер валидирует **последовательность и интервалы событий** (скрамбл выдан → проверка пройдена → готовность → старт → стоп → кадр собранного кубика), а не верит присланному числу
- Ключевые кадры (после скрамбла, в конце) перепроверяются на сервере

## R4. WebSocket-реалтайм и рассинхрон 🟠

**В чём проблема:** синхронный старт при разном пинге; переподключение посреди дуэли; игрок закрыл вкладку — сервер должен заметить. Кода больше, чем кажется.

**Митигация:**
- Старт по серверному сигналу с отсчётом 3-2-1 (компенсирует небольшой пинг)
- Heartbeat/ping для детекта отвала; состояние комнаты хранится на сервере, при reconnect клиент восстанавливает его
- Все ветки отвалов прописаны в userflow §5.4 — реализовать их сразу, а не «потом»

---

## R5. Холодный старт: пустой матчмейкинг 🟠

**В чём проблема:** первые недели онлайн 0–2 человека — дуэль не с кем играть, продукт кажется мёртвым.

**Митигация:**
- **Турнир недели — основной режим на старте** (асинхронный, работает при любом онлайне)
- **Дуэль по ссылке с другом** — добавить в MVP: без матчмейкинга, просто кидаешь ссылку конкретному человеку. Дёшево и решает проблему
- Позже: бот-соперник (V2), посев через кубинг-сообщества (форумы, тг-чаты, вузовские клубы)

---

## R6. Скоуп-крип у соло-разработчика 🟠

**В чём проблема:** MVP уже на 6 этапов; идей больше, чем времени; проект рискует остаться вечно недоделанным.

**Митигация:**
- Дисциплина: не начинать этап N+1, пока N не работает
- После Этапа 1 (соло-таймер со зрением) уже есть полезный продукт — можно показывать людям и собирать фидбек
- Все новые идеи — только в бэклог, не в текущий этап

---

## R7. Читерство 🟡

**В чём проблема:** соревновательный продукт + браузерный клиент = клиенту нельзя доверять. 100% защиты не существует.

**Митигация:**
- Скрамбл генерирует сервер; скрамбл турнира недели виден только после подтверждения попытки
- Серверная перепроверка кадров + валидация таймингов (см. R3)
- Цель — сделать читерство **дорогим**, а не невозможным; принять это в правилах
- Отвал после показа скрамбла турнира = попытка потрачена

---

## R8. Мобильные браузеры 🟡

**В чём проблема:** камера + кубик + две руки на столе с телефона — сомнительный UX; MediaPipe на слабых телефонах тормозит.

**Решение (принять до Этапа 1):** в MVP официально поддерживаем десктоп/ноутбук; на мобильных показываем экран «играй с компьютера». Мобильная поддержка — отдельный пункт бэклога.

## R9. Операционные мелочи, которые забывают 🟡

| Что | Риск | Решение |
|---|---|---|
| Письма подтверждения | Свой SMTP → спам | Сервис рассылки (Resend / Brevo, бесплатные тарифы) |
| Персональные данные | Почты пользователей = юр. требования | Политика конфиденциальности + согласие; явно написать «видео не покидает устройство, на сервер уходят только кадры проверки» |
| Ники/аватарки | Оскорбительный контент | Минимальный фильтр слов + жалоба в профиле (V2) |
| Споры о правилах | «Почему мне DNF?!» | Страница правил: ритуал, точность таймера, что считается DNF |
| Два устройства | Один аккаунт в двух дуэлях | Запрет второй активной дуэли на аккаунт |
| Название/домен | Занято | Проверить до привязки к названию |
| Понимание пользователей | Не видно, где люди отваливаются | Простая аналитика воронки: регистрация → первая сборка → первая дуэль |
