# Cubr — Решения проблем (технический уровень)

> Пара к [product-overview/risks.md](../product-overview/risks.md): там проблемы и стратегия, здесь — КАК конкретно решать, с алгоритмами и библиотеками.

---

## П1. Зрение кубика: цвета сливаются (белый/жёлтый, красный/оранжевый)

**Решение — три слоя:**

1. **Эталоны из профиля кубика с быстрой подстройкой** (утв. фича — [feature-cube-profiles](../product-overview/feature-cube-profiles.md)). Кубик регистрируется один раз: 6 граней → медианный цвет 9 наклеек каждой → 6 Lab-эталонов, сохраняются в профиль (`cubes.color_profile`). Перед каждой игрой игрок показывает ОДНУ грань собранного кубика → вычисляем сдвиг освещения (эталон↔наблюдение) и применяем ко всем 6 эталонам. Критерий: попарные ΔE между эталонами после сдвига ≥ порога различимости, иначе полная перекалибровка (6 граней). Собранный кубик показывается ПЕРВЫМ в ритуале (до скрамбла) — калибровка + подтверждение честного старта. (Изначально было «снимать эталон сессии с нуля каждый раз» — профиль сокращает шаг с ~20 до ~3 сек.)

2. **Правильное цветовое пространство.** Не сравнивай в RGB. Конвертируй в **Lab** (или HSV, но Lab лучше) и считай расстояние ΔE до каждого из 6 эталонов. Наклейка получает цвет ближайшего эталона.
   ```
   для каждой наклейки:
       lab = rgb2lab(медиана пикселей центра наклейки)
       цвет = argmin(ΔE(lab, эталон_i)) по i = 1..6
   ```
   Медиана центральной области наклейки (например, центральные 50%×50%), не среднее всего квадрата — так блики и границы не портят цвет.

3. **Глобальное ограничение 9×6.** На кубике ровно 9 наклеек каждого цвета. Вместо независимой классификации каждой наклейки решай задачу назначения: 54 наклейки × 6 цветов, у каждого цвета квота 9. Жадный вариант: отсортируй все пары (наклейка, цвет) по ΔE, назначай по возрастанию, пропуская цвета с исчерпанной квотой. Точный вариант — венгерский алгоритм. Это чинит большинство ошибок красный/оранжевый: даже если 2 наклейки сомнительные, квоты вынудят правильное распределение.

**Дополнительно:** перед чтением проверяй качество кадра — если средняя яркость слишком низкая/высокая или у эталонов ΔE между красным и оранжевым < порога, сразу проси игрока сменить свет, а не мучай его ошибками чтения.

## П2. Нахождение кубика и сетки 3×3 в кадре

**Решение (по возрастанию сложности, начни с простого):**

1. **MVP-вариант — рамка-гид.** Не ищи кубик, пусть игрок сам поместит его в рамку на экране (как сканер QR-кодов). Рамка задаёт область → дели её на сетку 3×3 → читай 9 центров. Работает сразу, «стоимость» — небольшая инструкция игроку.

2. **V2 — автодетект контура.** OpenCV.js: grayscale → Canny → findContours → ищи 4-угольный контур подходящей площади → perspectiveTransform в квадрат → сетка 3×3. Для stickerless-кубиков контур хуже — сегментируй по насыщенности (кубик ярче фона).

3. **V3 — лёгкая нейросеть.** Если классика достала: разметь ~200 своих кадров, дообучи маленький детектор (YOLO-n или подобный), сконвертируй в TF.js/ONNX-web. Но скорее всего рамки-гида хватит навсегда.

## П3. «Руки лежат на столе» без датчика глубины

**Решение — зона + неподвижность + конечный автомат:**

1. На экране две зоны («левая рука сюда, правая сюда»), внизу кадра.
2. MediaPipe Hands даёт 21 landmark на руку. Условие «рука в зоне»: центры ладоней (landmark 0, 9) внутри зоны.
3. Условие «лежит»: суммарное движение landmarks между кадрами < порога в течение **500 мс подряд** (неподвижная рука ≈ лежащая рука; висящая в воздухе всегда чуть дрожит — это и есть твой «датчик глубины»).
4. Конечный автомат с debounce на каждый переход:
   ```
   NO_HANDS → HANDS_IN_ZONE (обе руки в зонах ≥ 200 мс)
   HANDS_IN_ZONE → READY (движение < порога ≥ 500 мс)
   READY → SOLVING (рука покинула зону — старт таймера)
   SOLVING → STOPPED (обе руки в зонах ≥ 200 мс — стоп)
   ```
5. Пороги (мс, пиксели движения) вынеси в конфиг — будешь тюнить на живых людях в Этапе 0–1.

## П4. Точность таймера при 30 fps

**Решение:**

1. **Не привязывай таймер к кадрам камеры.** Таймер — `performance.now()`. Кадр лишь определяет МОМЕНТ события (рука ушла из зоны / вернулась).
2. Уточнение момента: событие произошло между кадром N-1 и N → бери середину интервала, погрешность ±16 мс при 30 fps. Для честной дуэли это ок: у обоих одинаковая погрешность.
3. `requestVideoFrameCallback` вместо `requestAnimationFrame` — даёт точный timestamp каждого кадра камеры.
4. Запроси у камеры 60 fps (`getUserMedia` constraints: `frameRate: {ideal: 60}`) — где поддерживается, погрешность вдвое меньше.
5. В правилах сайта честно напиши точность (±0.02–0.03 с). Спидкуберы поймут — у StackMat тоже есть допуски.

## П5. Клиенту нельзя доверять (тайминги, читы)

**Решение — сервер как арбитр:**

1. **События, не итоги.** Клиент шлёт по WebSocket поток событий с клиентскими таймстампами: `scramble_shown`, `scramble_verified`, `hands_ready`, `solve_start`, `solve_stop`, `cube_verified`. Сервер проставляет свои server-side таймстампы получения.
2. **Валидация последовательности:** события в правильном порядке; интервалы правдоподобны (проверка скрамбла не может занять 0 сек; сборка < 4 сек у игрока со средним 25 сек → флаг); клиентское время сборки vs серверная разница `solve_stop − solve_start` расходятся не больше чем на допуск (2–3 сек на сетевой джиттер).
3. **Кадры-доказательства:** на `scramble_verified` и `cube_verified` клиент прикладывает JPEG-кадр (это килобайты, не видео). Сервер перечитывает состояние кубика тем же алгоритмом (OpenCV, Python) и сверяет: после скрамбла — с эталоном скрамбла, в конце — с собранным.
4. **Скрамбл только от сервера**, выдаётся в момент старта комнаты. Скрамбл турнира недели — только после подтверждения попытки (см. П8).
5. Результат = `valid` только после всех проверок; иначе `rejected` + победа сопернику.

## П6. WebSocket: рассинхрон, отвалы, переподключение

**Решение:**

1. **Состояние комнаты живёт на сервере** (в памяти + бэкап в Redis/БД): фаза каждого игрока, таймстампы, скрамбл. Клиент — только отображение.
2. **Синхронный старт:** оба в READY → сервер шлёт `countdown_start` с серверным временем старта через 3 сек. Клиент показывает 3-2-1 от своего получения; допуск на пинг уже включён в валидацию П5.
3. **Heartbeat:** ping/pong каждые 5 сек; нет ответа 15 сек → игрок считается отвалившимся, сопернику показываем статус.
4. **Reconnect:** клиент хранит `room_id` + `session_token`; при обрыве переподключается с ними, сервер отдаёт полный снапшот состояния комнаты (`фаза, твой статус, статус соперника, оставшиеся таймауты`), клиент восстанавливает экран.
5. **Таймауты по фазам** (сервер enforce'ит): подготовка ≤ 3 мин, сборка ≤ 10 мин. Просрочил → DNF, комната завершает дуэль.
6. В FastAPI: один `ConnectionManager` с dict `room_id → {player_id → websocket}`, всё асинхронно. Для MVP на одном сервере Redis не обязателен — хватит памяти процесса.

## П7. Холодный старт: не с кем играть

**Решение:**

1. **Дуэль по ссылке** (в MVP): кнопка «Пригласить друга» → создаётся комната с токеном → ссылка `site/duel/join/<token>` → друг переходит (после логина) и попадает прямо в комнату. Технически это твоя же комната дуэли минус матчмейкинг — почти бесплатно.
2. **Турнир недели как главный экран** при пустом онлайне: если в очереди матчмейкинга никого > 60 сек — предлагай «пока сыграй попытку недели» вместо бесконечного спиннера.
3. **Посев:** кубинг-чаты в Telegram, VK-сообщества, клуб своего вуза; недельный турнир — идеальный формат «скинул ссылку в чат, все соревнуются асинхронно».
4. **Бот-соперник (V2):** проигрываешь записанный таймлайн реальной сборки подходящего уровня — сопернику показываются те же статусы. Честно пометить «бот».

## П8. Читы в турнире недели

**Решение:**

1. Скрамбл показывается только ПОСЛЕ клика «Сделать попытку» + подтверждения.
2. В момент подтверждения сервер создаёт запись `attempt (status=started)`. Перезагрузка/уход после этого → `attempt = DNF`. Одна запись на игрока в неделю — enforce на уровне БД (unique constraint `user_id + tournament_id`).
3. Кадры и тайминги валидируются как в П5.
4. Смена скрамбла — cron/APScheduler на сервере в ночь на понедельник: финализировать таблицу, начислить кубки, создать новый турнир.

## П9. Письма уходят в спам

**Решение:** не поднимай свой SMTP. Возьми Resend / Brevo (бесплатные тарифы: тысячи писем в месяц). Подключи свой домен, настрой SPF + DKIM (у сервисов пошаговая инструкция). Письма нужны трёх видов: подтверждение почты, сброс пароля, (позже) уведомления. Шли асинхронно (background task в FastAPI), чтобы регистрация не висела на отправке.

## П10. Персональные данные и приватность камеры

**Решение:**

1. Страница «Политика конфиденциальности» + чекбокс согласия при регистрации.
2. Прямо на лендинге и в онбординге: **«Видео не покидает ваше устройство. Обработка идёт в браузере; на сервер отправляются только отдельные кадры кубика для проверки честности.»** Это и правда, и конкурентное преимущество.
3. Кадры-доказательства: храни только до валидации + короткий срок для разборов споров (например 7 дней), потом автоудаление. Кадрируй по рамке кубика — лицо в кадр доказательства не попадает.
4. Пароли — argon2 (fastapi-users умеет), токены сброса — одноразовые, с TTL 1 час.

## П11. Один аккаунт с двух вкладок/устройств

**Решение:** при входе в дуэль/попытку сервер проверяет: есть ли активная комната у `user_id`. Есть → новой вкладке отдаём «У тебя уже идёт дуэль» с кнопкой «перейти в неё» (reconnect по П6-4). WebSocket-сессии считаем по `user_id`, не по токену вкладки.
