## Часть A. Исправление порядка ритуала (баг документации)

### A.1 Проблема
В текущих документах и прототипе логика нарушена: скрамбл показывается ДО того, как система увидела собранный кубик. Это нелогично: калибровка цветов и подтверждение стартового состояния требуют показать камере именно СОБРАННЫЙ кубик — до любого перемешивания.

### A.2 Правильный порядок ритуала (заменяет userflow §5.1, шаги 1–3)

```
1. [НОВОЕ МЕСТО] Игрок показывает камере СОБРАННЫЙ кубик
   → система: калибрует/подстраивает цвета (см. Часть B)
   → система: подтверждает честное стартовое состояние (кубик собран)
2. Сервер выдаёт скрамбл (в дуэли — одинаковый обоим)
3. Игрок перемешивает по визуальной инструкции или нотации
   (см. spec №7 — scramble-visual)
4. Показывает перемешанный кубик камере → сверка с эталоном скрамбла
5. Две руки + кубик на стол → готовность
6. Синхронный старт → сборка → руки на стол → стоп
7. Показ собранного кубика → подтверждение → результат
```

### A.3 Исправления в прототипе (Этап 0)
- [ ] Поменять порядок фаз конечного автомата сценария: CALIBRATE_SOLVED → SCRAMBLE_SHOWN → SCRAMBLE_VERIFY → READY → SOLVING → STOPPED → SOLVE_VERIFY
- [ ] Экран калибровки — первый экран цикла, не «где-то в настройках»

## Часть B. Профили кубиков (новая фича, утверждена)

### B.1 Идея заказчика
Игрок регистрирует свои кубики один раз: показывает 6 граней собранного кубика, даёт название («GAN 356», «старый школьный»). Сайт запоминает цветовые профили. Дальше перед игрой игрок просто выбирает, каким кубиком собирает, — и система уже знает его цвета. Кубиков может быть несколько.

### B.2 Решение ПМ: профиль + быстрая подстройка (обязательное дополнение)

**Проблема, которую нельзя игнорировать:** цветовой профиль снимается при конкретном освещении. Другой свет (вечер, другая комната) → сохранённые эталоны врут → красный/оранжевый снова путаются. Полностью доверять сохранённому профилю нельзя — это подорвало бы главную митигацию риска R1.

**Решение — трёхуровневая схема:**

| Уровень | Когда | Что делает игрок | Время |
|---|---|---|---|
| **Регистрация кубика** | Один раз на кубик | Показывает 6 граней собранного кубика, называет его | ~20 сек |
| **Быстрая подстройка** | Каждую сессию/игру (шаг 1 ритуала) | Показывает ОДНУ любую грань собранного кубика | ~3 сек |
| **Полная перекалибровка** | Если подстройка не сошлась | Показывает 6 граней заново (профиль обновляется) | ~20 сек |

**Как работает быстрая подстройка:** по одной грани система видит 9 наклеек одного известного цвета → вычисляет сдвиг между сохранённым эталоном и текущим наблюдением (по сути коррекция баланса белого/яркости) → применяет этот сдвиг ко всем 6 эталонам профиля. Критерий успеха: после сдвига попарные расстояния ΔE между 6 эталонами остаются above порога различимости; иначе → полная перекалибровка.

**Что это даёт:** шаг 1 ритуала сокращается с 15–20 сек до ~3 сек, при этом честность сохраняется — система в начале каждой игры всё равно видит собранный кубик (подтверждение стартового состояния из части A остаётся: одна грань + быстрый прогон остальных пяти по упрощённой проверке, либо полный показ — решить на прототипе, что достаточно).

### B.3 UX

**Регистрация кубика (Настройки → «Мои кубики» → «Добавить кубик»):**
1. Мастер: «покажи белую грань» → … 6 граней с подсказками
2. Поля: название (обязательно), заметка (опционально)
3. Превью считанных цветов («вот как я вижу твой кубик») → подтвердить
4. Первый зарегистрированный кубик автоматически «основной»

**Экран «Мои кубики»:**
- Список: название, миниатюра палитры (6 цветов), дата, метка «основной»
- Действия: переименовать, сделать основным, перекалибровать, удалить
- Лимит в MVP: до 5 кубиков на аккаунт

**Выбор кубика перед игрой:**
- В лобби / перед входом в дуэль: селектор «Кубик: [основной ▾]» — по умолчанию основной, менять не обязательно
- Если кубиков нет (новый игрок) → регистрация первого кубика встроена в онбординг (заменяет старый шаг «проверка камеры» → теперь «проверка камеры + регистрация кубика»)

**В ритуале (шаг 1):**
- «Покажи собранный кубик [название]» → одна грань → ✅ (или просьба полной перекалибровки)
- Показал не тот кубик (цвета не бьются ни с одним профилем после подстройки) → «Похоже, это другой кубик. Выбрать другой профиль / зарегистрировать новый?»

### B.4 Модель данных (добавить в project.md §5)

```
cubes:  id, user_id, name, note?, is_primary,
        color_profile JSONB,   -- 6 эталонов в Lab: {W:[L,a,b], Y:..., R:..., O:..., B:..., G:...}
        created_at, recalibrated_at
solves: + cube_id (FK, nullable для старых записей)
```

Профиль храним в Lab (не RGB) — в нём же считаем ΔE и подстройку.

### B.5 Бонус: кубик как сущность продукта (в бэклог/roadmap)
- Статистика по кубикам: «на GAN 356 average лучше на 1.2 сек» — куберы ОБОЖАЮТ сравнивать железо
- Кубик в публичном профиле игрока (часть идентичности, соцсеть)
- V3: «каким кубиком собран этот рекорд» в таблицах лидеров

### B.6 План работ

**Этап 0 (прототип):**
- [ ] Исправить порядок фаз (часть A.3)
- [ ] Снятие профиля с 6 граней → сохранение в localStorage (без сервера)
- [ ] Быстрая подстройка по одной грани + критерий «сошлось/не сошлось»
- [ ] Тест: профиль снят при дневном свете → подстройка при лампе → точность чтения не деградирует

**Этап 2 (аккаунты):**
- [ ] Таблица cubes, CRUD-эндпоинты, лимит 5
- [ ] Мастер регистрации кубика + экран «Мои кубики» в настройках
- [ ] Регистрация первого кубика в онбординге
- [ ] Селектор кубика перед игрой; solve.cube_id пишется в результат

### B.7 Критерии приёмки
1. Новый игрок регистрирует кубик в онбординге ≤ 30 сек и сразу играет
2. Возвращающийся игрок проходит шаг 1 ритуала за ~3 сек (одна грань)
3. Смена освещения между сессиями не ломает чтение (тест B.6)
4. Игрок с двумя кубиками переключается между ними без перекалибровки
5. Показ незарегистрированного кубика детектится и ведёт к понятному действию
