# Раннбук деплоя — Cubr

> Порядок шагов, а не описание архитектуры. Каждый шаг заканчивается проверкой,
> которую видно глазами: если проверка не сходится — дальше не идём, потому что
> следующий шаг будет чинить не то.

## Что где живёт

Всё на одной машине (VPS), три контейнера в одной docker-сети:

```
интернет :443 ──► Caddy ──┬─► статика фронта (/srv/cubr/www)
                          └─► /api/*  ──► api:8000 (FastAPI, 1 воркер)
                                              │
                                          db:5432 (Postgres 16, только внутри сети)
```

| Кусок | Где | Чем задан в репозитории |
|---|---|---|
| SPA (React) | статика на том же сервере, отдаёт Caddy | `frontend/`, собирается локально, `rsync` в `/srv/cubr/www` |
| API (FastAPI) | контейнер `api` на VPS | `backend/Dockerfile`, `deploy/docker-compose.yml` |
| Postgres | контейнер `db` на VPS, порт не публикуется | `deploy/docker-compose.yml`, миграции — `alembic upgrade head` |
| TLS / реверс-прокси | контейнер `caddy` на VPS | `deploy/Caddyfile` |
| Почта | Resend | ключ в `.env` на сервере, DNS-записи у регистратора домена — отложено, см. ниже |
| Финализация попыток | cron на сервере | `docker compose run --rm api python -m app.jobs.finalize` |
| Бэкапы | cron на сервере | `pg_dump` в `/srv/cubr/backups`, хранение 14 дней |

Фронт и API живут на **одном origin** — Caddy проксирует `/api/*` на
`api:8000` и отдаёт всё остальное как SPA со фолбэком на `index.html`. Это не
украшение: cookie авторизации `SameSite=Lax` не уедет на чужой origin, и без
единого origin вход не работает вообще. Тем же способом закрыт вопрос CORS —
настраивать его отдельно не нужно.

**Реплика ровно одна, воркер ровно один.** Комнаты дуэлей лежат в памяти
одного процесса (`app/services/duel_manager.py`), поэтому `WEB_CONCURRENCY=1`
и `--workers 1` в `Dockerfile`. Приложение откажется стартовать при
`WEB_CONCURRENCY > 1` — лучше явный отказ, чем дуэли, которые разваливаются
через раз. `backend/railway.json` больше не используется для деплоя (Railway
как платформа не используется), но файл оставлен в репозитории — он
по-прежнему документирует то же ограничение (`numReplicas: 1`) для любого, кто
будет читать код бэкенда.

Захочется горизонтально масштабироваться — сначала выносим состояние комнат в
Redis, отдельной задачей.

**Postgres наружу не смотрит.** Порт 5432 не публикуется в хост вообще —
только `api` внутри docker-сети `cubr` может к нему достучаться.

## 0. До первого деплоя

- [ ] Домен куплен, доступ к его DNS есть (`cubr-game.ru`, Selectel).
- [ ] Сервер поднят: Ubuntu 24.04, Docker + Compose, пользователь `deploy` с
      sudo без пароля и в группе `docker`, firewall (`ufw`) разрешает только
      22/80/443, SSH — только по ключу.
- [ ] Сгенерированы пять секретов, каждый — своей командой, **на сервере**, не
      копией соседа:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
```

Нужны `SECRET`, `RESET_VERIFY_SECRET`, `SCRAMBLE_SIGN_SECRET`,
`DUEL_SIGN_SECRET`, `UNSUBSCRIBE_SIGN_SECRET`, плюс пароль Postgres — итого
шесть команд, шесть разных значений. Они разные по смыслу: утёк один — не должен открывать остальные.
Приложение откажется стартовать, если в значении встретится `change-me` /
`placeholder` / `example`, — плейсхолдеры из `.env.example` в прод не проедут.

Секреты живут **только** в `/srv/cubr/.env` на сервере, права `600`, владелец
`deploy`. В репозиторий, в Memory Bank, в переписку — никогда.

## 1. Артефакты деплоя в репозитории

`deploy/docker-compose.yml`, `deploy/Caddyfile`, `deploy/.env.example` —
описывают три сервиса (`db`, `api`, `caddy`) в одной сети с фиксированной
подсетью `172.28.0.0/16` и статическим IP `172.28.0.10` у `caddy`.

Статический IP у Caddy важен: `app/main.py` доверяет `TRUSTED_PROXIES` по IP
для `X-Forwarded-For` и рейт-лимитов. Без фиксации Docker выдал бы контейнеру
случайный адрес из подсети, и после каждого перезапуска список бы врал —
либо клиент подделывает IP и обходит лимиты, либо весь сайт считается одним
клиентом.

Проверка: `docker compose -f deploy/docker-compose.yml config` разбирает файл
без ошибок.

Все три сервиса делят один `logging`-профиль (`x-logging` в верху файла):
json-file, `max-size: 10m`, `max-file: 3`. Без этого лог растёт неограниченно —
на диске 25 ГБ, столько отдавать одним контейнерам не с руки. Применяется
через `docker compose up -d` (пересоздаёт контейнеры — данные не трогает,
`pgdata` живёт в отдельном volume).

Проверка: `docker inspect <контейнер> --format '{{json .HostConfig.LogConfig}}'`
показывает `max-size: 10m`, `max-file: 3`.

## 2. Сборка фронта — локально, не на сервере

```bash
cd frontend && npm ci && npm run build
```

`npm run build` на 1 vCPU / 2 ГБ рискует упереться в память, а собранный
`dist/` байт в байт тот же, что и с ноутбука. Есть `postbuild`-проверка бюджета
входного чанка (320 кБ) — если она не проходит, это регрессия, а не повод
собирать иначе.

Залить на сервер:

```bash
rsync -az --delete frontend/dist/ deploy@<сервер>:/srv/cubr/www/
```

Проверка: на сервере `ls /srv/cubr/www/index.html` существует, размер каталога
сопоставим с локальным `dist`.

## 3. База данных и API на сервере

`deploy/docker-compose.yml` собирает `api` из `../backend`
(`build: context: ../backend`) — это относительный путь от самого
`docker-compose.yml`, так что раскладка на сервере обязана быть такой же, как
в репозитории: `docker-compose.yml`/`Caddyfile`/`.env` лежат в `/srv/cubr`,
исходники бэкенда — в `/srv/backend` (владелец `deploy` у обоих). Залить их
можно так же, как фронт — `rsync` списком отслеженных git-файлов
(`git -C backend ls-files`), чтобы не утащить `.venv`/`.env`/тесты:

```bash
cd backend && git ls-files > /tmp/backend-files.txt
rsync -az -e ssh --files-from=/tmp/backend-files.txt . deploy@<сервер>:/srv/backend/
```

На сервере в `/srv/cubr` (владелец `deploy`) лежат `docker-compose.yml`,
`Caddyfile` и `.env` (см. `deploy/.env.example` — там же список, какие значения
обязаны отличаться от `backend/.env.example`; главное отличие — `DATABASE_URL`
обязан начинаться с `postgresql+asyncpg://`, движок асинхронный, с голой
схемой `postgresql://` он не поднимется).

```bash
docker compose up -d db
docker compose run --rm api alembic upgrade head
docker compose up -d
```

Упала миграция — не поднимать `api`, разбираться, что случилось: старая версия
(если была) продолжает работать, новая просто не стартует.

Проверка: `docker compose ps` — все три сервиса `healthy`/`running`;
`docker compose exec -T api python -c "import app.main"` не падает;
`curl -s localhost:8000/health` изнутри сети отдаёт 200 (внутри — настоящий
`SELECT 1`, так что это проверка и базы тоже).

## 4. Домен и HTTPS

`SITE_DOMAIN` в `.env` — домен, для которого Caddy сам выпустит сертификат
Let's Encrypt при старте. Нужна рабочая A-запись на IP сервера **до** старта
Caddy с этим доменом.

```bash
dig +short A cubr-game.ru
```

На 2026-08-23 A-запись есть, прод стоит на `cubr-game.ru`, и fallback-адрес
`135-106-181-244.sslip.io` **перестал открываться**: сертификат выпущен под
`SITE_DOMAIN`, а на чужой SNI Caddy отвечает `tlsv1 alert internal error`.
Это ожидаемо, а не поломка — сервер жив (порт 80 отдаёт 308).

Если A-записи ещё нет — использовать временный `SITE_DOMAIN` вида
`<IP-через-дефисы>.sslip.io` (`sslip.io` резолвит IP прямо из имени, Let's
Encrypt такие имена подписывает). При смене домена **вместе** меняются четыре
переменные: `SITE_DOMAIN`, `CORS_ORIGINS`, `DUEL_ALLOWED_WS_ORIGINS`,
`FRONTEND_URL` — рассогласование даёт рабочую страницу, на которой не
работает ни вход, ни дуэли.

Let's Encrypt позволяет 5 выпусков сертификата на домен в неделю — не
зацикливать выпуск при отладке.

Проверка: `curl -sI https://<домен>/` отдаёт 200 и валидный сертификат;
`curl -s https://<домен>/api/health` отдаёт 200; прямой заход на
`https://<домен>/rules` отдаёт страницу, а не 404 (проверка SPA-фолбэка —
`try_files … /index.html` в `deploy/Caddyfile`).

## 5. Почта: SPF и DKIM

Без этих записей письма подтверждения уходят в спам — а без подтверждения
почты человек не заканчивает регистрацию. **Отложено осознанно**: письма
всё равно требуют SPF/DKIM на своём домене, регистрация по email и паролю от
их отсутствия не страдает (подтверждение почты вход не гейтит).

1. В Resend добавить домен отправки (тот, что в `EMAIL_FROM`).
2. Добавить у регистратора DNS-записи, которые Resend показывает (SPF — кому
   разрешено слать письма от домена, DKIM — подпись, по которой письмо
   проверяют).
3. Дождаться, пока Resend отметит домен проверенным, вписать `RESEND_API_KEY`
   в `/srv/cubr/.env`, `docker compose up -d api`.

Проверка: зарегистрировать тестовый аккаунт на почту в Gmail, письмо приходит
во «Входящие», а не в спам.

## 6. Google OAuth

Тоже отложено осознанно: нужен заранее зарегистрированный redirect-адрес.

Redirect URL в консоли Google должен совпадать с `GOOGLE_OAUTH_REDIRECT_URL`
символ в символ: `https://<домен>/api/auth/google/callback`. Расхождение в
хвостовом слэше или в `www` — это ошибка `redirect_uri_mismatch` и больше
ничего.

Проверка: вход через Google возвращает на сайт залогиненным.

## 7. Cron — финализация попыток и бэкапы

Попытка турнира или скрамбла дня, начатая и не отправленная, висит в статусе
`started`, пока её не подметут. Метёт отдельная задача, идемпотентная —
запускать можно как угодно часто:

```cron
*/5 * * * * cd /srv/cubr && /usr/bin/docker compose run --rm api python -m app.jobs.finalize >> /var/log/cubr-finalize.log 2>&1
```

Пять минут — борд не должен показывать зависшую попытку дольше этого
(обоснование — `backend/README.md` § Scheduled finalize). Планировщик —
внешний (host-cron на том же образе), не внутри веб-процесса:
внутрипроцессный планировщик умирает вместе с воркером и дублируется вместе с
ним.

Развёртка писем о новых сообщениях в чате — та же схема, отдельная
идемпотентная задача, раз в минуту (сообщение с `notify_after` не должно ждать
письма дольше минуты сверх пятиминутной задержки):

```cron
* * * * * cd /srv/cubr && /usr/bin/docker compose run --rm api python -m app.jobs.chat_notify >> /var/log/cubr-chat-notify.log 2>&1
```

Джоба безопасна при наложении запусков (claim-then-send с повторной проверкой
`notify_state = 'pending'`) и печатает сводку `chat_notify_sweep` каждый запуск,
включая нулевой. Требует секрет `UNSUBSCRIBE_SIGN_SECRET` в `/srv/cubr/.env`
(см. §0 — генерируется на сервере, как остальные подписи).

Ежедневный дамп базы, хранить 14 дней:

```cron
30 4 * * * cd /srv/cubr && docker compose exec -T db pg_dump -U cubr cubr | gzip > backups/cubr-$(date +\%F).sql.gz && find backups -name 'cubr-*.sql.gz' -mtime +14 -delete
```

Проверка: запустить finalize руками — отрабатывает и печатает, сколько
попыток подмёл (на пустой базе ноль, это нормально); `pg_dump` создаёт
непустой архив; `gunzip -t` подтверждает целостность.

### Проверка восстановления бэкапа

Бэкап, из которого никто ни разу не разворачивался, — это не бэкап, а
надежда. Разворачивать в **отдельную, одноразовую** базу внутри того же
контейнера `db`, никогда не поверх боевой `cubr`:

```bash
cd /srv/cubr
DUMP=$(ls -t backups/cubr-*.sql.gz | head -1)
docker compose exec -T db psql -U cubr -d cubr -c "CREATE DATABASE cubr_restore_test;"
gunzip -c "$DUMP" | docker compose exec -T db psql -U cubr -d cubr_restore_test -v ON_ERROR_STOP=1 -q
docker compose exec -T db psql -U cubr -d cubr_restore_test -c "\dt"
docker compose exec -T db psql -U cubr -d cubr_restore_test -c "select version_num from alembic_version;"
docker compose exec -T db psql -U cubr -d cubr -c "DROP DATABASE cubr_restore_test;"
```

Проверка: все таблицы из `\dt` совпадают со списком в живой `cubr`;
`version_num` в `alembic_version` совпадает с именем последнего файла в
`backend/migrations/versions/` (текущая голова — там нет ветвления, файлы
пронумерованы по порядку, у головы никто не указывает её в своём
`down_revision`). После проверки — обязательно `DROP DATABASE
cubr_restore_test`, живую `cubr` не трогать.

### Ротация логов

`/etc/logrotate.d/cubr` — источник в репозитории, `deploy/logrotate.d/cubr`.
Ставится вручную (logrotate не читает `/srv/cubr`):

```bash
sudo cp deploy/logrotate.d/cubr /etc/logrotate.d/cubr
sudo chown root:root /etc/logrotate.d/cubr && sudo chmod 644 /etc/logrotate.d/cubr
```

Ротирует `/var/log/cubr-*.log` (finalize, бэкап, liveness — все host-cron
логи разом), еженедельно, 4 копии, `copytruncate`. Логи самих контейнеров
Docker ротирует отдельно — `logging.options.max-size`/`max-file` в
`deploy/docker-compose.yml` (см. § 1).

Проверка: `sudo logrotate -d /etc/logrotate.d/cubr` разбирает конфиг без
ошибок (debug-режим ничего не ротирует, только проверяет).

### Liveness-проверка

`deploy/scripts/liveness-check.sh`, на сервере — `/srv/cubr/scripts/`, cron
каждые 5 минут:

```cron
*/5 * * * * /srv/cubr/scripts/liveness-check.sh
```

Дергает `/` и `/api/health` по публичному HTTPS, пишет каждый прогон (успех
и неудачу) в `/var/log/cubr-liveness.log`. Перезапускает соответствующий
контейнер (`caddy` или `api`) только после **трёх подряд** неудач — не по
одному сбою, разовый таймаут это шум, а не авария. После перезапуска не
трогает тот же пробник ещё 30 минут (`COOLDOWN`), даже если он продолжает
падать — иначе получился бы дребезжащий авто-рестарт, который хуже, чем его
отсутствие; после cooldown дальше разбирается человек, не cron. Состояние
(счётчики подряд-идущих неудач, метки времени последнего рестарта) — простые
файлы в `/var/lib/cubr-liveness/`.

Проверка: `/srv/cubr/scripts/liveness-check.sh` руками — пишет `site OK` /
`api OK` в лог при здоровом стеке; при остановленном `api`
(`docker compose stop api`) три запуска подряд пишут `FAIL,
consecutive=1/2/3`, на третьем — `restarting container: api`, `api` вновь
`Up`, `/api/health` снова 200.

### Restart-политики

Все три сервиса — `restart: unless-stopped`. Проверка не чтением файла, а
живым перезапуском демона: `sudo systemctl restart docker`, затем `docker
compose ps` — все три контейнера должны подняться сами, без ручного `docker
compose up`.

## Смоук после деплоя

Прогнать в проде живьём, по порядку — каждый пункт трогает свой кусок:

- [ ] `https://<домен>/` отдаёт лендинг.
- [ ] `/rules` и `/privacy` открываются прямой ссылкой.
- [ ] `/api/health` → 200.
- [ ] Регистрация нового пользователя через API → 201.
- [ ] Вход → приходит cookie с флагами `Secure`, `HttpOnly`, `SameSite=Lax`.
- [ ] `GET /api/users/me` с этой cookie → 200.
- [ ] `GET /api/scramble` → строка скрамбла и `scramble_token`.
- [ ] `POST /api/solves` с этим токеном → 201, сборка появляется в истории.
- [ ] `GET /api/daily/current` под аутентификацией → 200, аноним → 401.
- [ ] Рейт-лимит: 11 попыток входа подряд с одного IP → 429 (проверяет заодно,
      что `TRUSTED_PROXIES` настроен верно).
- [ ] Смена языка RU/EN на странице не ломает её.
- [ ] Регистрация → письмо пришло во «Входящие» → ссылка подтверждает почту
      (после Этапа 5, когда включён Resend).
- [ ] Вход через Google (после Этапа 6).
- [ ] Дуэль по ссылке между двумя браузерами (нужна камера, живая проверка).
- [ ] Открыть сайт с телефона — показывается гейт «нужен компьютер», а не
      сломанный ритуал.

## Обновление продакшена

Выкатка — один скрипт, а не последовательность команд по памяти:

```bash
deploy/scripts/deploy.sh
```

Порядок шагов внутри выбран так, чтобы неудача останавливала выкатку ДО того,
как продакшен изменится. Сборка фронта идёт локально и первой: сломанная сборка
не должна доехать до сервера. Миграции накатываются, пока работает СТАРЫЙ
контейнер, — упавшая миграция оставляет прод ровно таким, каким он был. Статика
заливается последней, уже после того как новый бэкенд поднялся.

Сборка идёт на ноутбуке, а не на сервере: там одно ядро и два гигабайта, и
vite-сборка рискует упереться в память. Ради этого же на сервере нет ни
инструментов сборки, ни доступа к репозиторию — там лежит только копия
исходников бэкенда (`/srv/backend`) и готовая статика (`/srv/cubr/www`).

Скрипт заканчивается смоуком по трём адресам и явно говорит, подтверждена
выкатка или нет. Не подтверждена — смотреть логи командой, которую он печатает.

## Откат

Фронт: пересобрать `frontend/dist/` из предыдущего коммита локально,
`rsync` в `/srv/cubr/www` — быстрее, чем хранить версии на сервере, и не
требует лишней инфраструктуры при таком масштабе.

API: `git checkout <предыдущий-тег-или-коммит> -- backend`, затем
`docker compose build api && docker compose up -d api`. **Осторожно с
миграциями** — откат кода не откатывает схему. Если в выкатке была миграция,
ломающая совместимость со старым кодом, сначала
`docker compose run --rm api alembic downgrade -1`, и только потом откат
образа. Поэтому миграции, удаляющие или переименовывающие колонки, стоит
разбивать на две выкатки: сначала код, который умеет и так и так, потом
схема.

База: восстановление из `/srv/cubr/backups/cubr-<дата>.sql.gz` во временную
базу для проверки, и только после этого — в `db`, если решение подтверждено.
