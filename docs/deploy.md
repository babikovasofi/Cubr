# Раннбук деплоя — Cubr

> Порядок шагов, а не описание архитектуры. Каждый шаг заканчивается проверкой,
> которую видно глазами: если проверка не сходится — дальше не идём, потому что
> следующий шаг будет чинить не то.
>
> Названия пунктов в веб-интерфейсах Vercel/Railway со временем меняются —
> смысл шага важнее точной подписи кнопки.

## Что где живёт

| Кусок | Где | Чем задан в репозитории |
|---|---|---|
| SPA (React) | Vercel | `frontend/vercel.json`, root directory = `frontend` |
| API (FastAPI) | Railway | `backend/Dockerfile`, `backend/railway.json` |
| Postgres | Railway | managed-сервис, миграции — `alembic upgrade head` |
| Почта | Resend | ключ в переменных API, DNS-записи у регистратора домена |
| Финализация попыток | внешний cron | `python -m app.jobs.finalize` |

Фронт и API живут на разных origin, но браузер об этом не знает: Vercel
переписывает `/api/*` на адрес Railway (`frontend/vercel.json`). Это не
украшение — cookie авторизации `SameSite=Lax` не уедет на чужой origin, и без
переписывания вход не работает вообще.

**Реплика ровно одна.** Комнаты дуэлей лежат в памяти одного процесса
(`app/services/duel_manager.py`), поэтому `WEB_CONCURRENCY=1`, `numReplicas: 1`
в `backend/railway.json`, и `--workers 1` в `Dockerfile`. Приложение откажется
стартовать при `WEB_CONCURRENCY > 1` — лучше явный отказ, чем дуэли, которые
разваливаются через раз. Захочется горизонтально масштабироваться — сначала
выносим состояние комнат в Redis, отдельной задачей.

## 0. До первого деплоя

- [ ] Домен куплен, доступ к его DNS есть.
- [ ] Аккаунты: Vercel, Railway, Resend, Google Cloud (для OAuth).
- [ ] Сгенерированы четыре секрета, каждый — своей командой, не копией соседа:

```bash
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

Нужны `SECRET`, `RESET_VERIFY_SECRET`, `SCRAMBLE_SIGN_SECRET`,
`DUEL_SIGN_SECRET`. Они разные по смыслу: утёк один — не должен открывать
остальные. Приложение откажется стартовать, если в значении встретится
`change-me` / `placeholder` / `example`, — плейсхолдеры из `.env.example` в
прод не проедут.

Секреты живут в переменных окружения платформы. В репозиторий, в Memory Bank, в
переписку — никогда.

## 1. База данных

1. Создать managed Postgres в Railway.
2. В переменных API-сервиса задать `DATABASE_URL`, взяв ссылку на переменную
   базы, и **поменять схему на `postgresql+asyncpg://`**. Платформа отдаёт
   `postgresql://…`; наш движок асинхронный, с голой схемой он не поднимется.

Проверка: строка начинается с `postgresql+asyncpg://`.

## 2. API на Railway

1. Новый сервис из этого репозитория, root directory — `backend`.
   Сборка пойдёт по `backend/Dockerfile` (это задано в `backend/railway.json`).
2. Заполнить переменные окружения по списку `backend/.env.example` — там у
   каждой строки, где локальное значение в проде неверно, стоит пометка
   `# prod:`. Минимум, что обязано отличаться от локального:
   - `APP_ENV` — что угодно, кроме `local` (от этого зависит флаг `Secure` у cookie);
   - `CORS_ORIGINS`, `DUEL_ALLOWED_WS_ORIGINS` — реальные origin сайта;
   - `FRONTEND_URL` — `https://<домен>`;
   - `GOOGLE_OAUTH_REDIRECT_URL` — `https://<домен>/api/auth/google/callback`;
   - `TRUSTED_PROXIES` — прокси платформы;
   - четыре секрета;
   - `RESEND_API_KEY`.
3. Миграции накатываются сами: `preDeployCommand` в `backend/railway.json`
   выполняет `alembic upgrade head` перед тем, как новая версия примет трафик.
   Упала миграция — деплой не состоялся, старая версия продолжает работать.

Проверка: `curl https://<railway-домен>/health` отдаёт ответ со статусом 200
(внутри — настоящий `SELECT 1`, так что это проверка и базы тоже).

### Про `TRUSTED_PROXIES`

Это список тех, кому мы верим, когда они говорят «настоящий IP клиента вот
такой» (заголовок `X-Forwarded-For`). По этому IP работают все рейт-лимиты.
Список слишком широкий — клиент подделает свой IP и обойдёт лимиты; слишком
узкий — весь сайт считается одним клиентом и упирается в лимит вдвоём.
Правильное значение — адрес прокси платформы; после деплоя проверяется тем, что
рейт-лимит срабатывает на одном браузере и не срабатывает на двух.

## 3. Фронт на Vercel

1. Новый проект из репозитория, root directory — `frontend`, пресет Vite.
2. В `frontend/vercel.json` вписать реальный адрес Railway вместо
   `REPLACE_WITH_BACKEND_URL_AT_DEPLOY.example.com` и закоммитить.

Подставить его переменной окружения нельзя: Vercel читает `vercel.json` из
репозитория **до** сборки. Поэтому прод-сборка с оставшимся плейсхолдером
падает намеренно — `frontend/scripts/check-api-proxy.mjs`. Иначе получился бы
сайт, который открывается, выглядит целым и молча 404-ит каждый запрос к API.

Проверка: открыть сайт, зайти в DevTools → Network, увидеть, что запросы идут на
`/api/...` собственного домена и отвечают не 404.

## 4. Домен и HTTPS

1. Привязать домен к проекту Vercel, добавить у регистратора DNS-записи, которые
   он попросит.
2. Сертификат Vercel выпустит сам. Дождаться, пока станет валидным.
3. Только после этого проверить вход: cookie авторизации помечена `Secure`
   (везде, кроме `APP_ENV=local`) и по http просто не поедет.

## 5. Почта: SPF и DKIM

Без этих записей письма подтверждения уходят в спам — а без подтверждения почты
человек не заканчивает регистрацию.

1. В Resend добавить домен отправки (тот, что в `EMAIL_FROM`).
2. Добавить у регистратора DNS-записи, которые Resend показывает (SPF — кому
   разрешено слать письма от домена, DKIM — подпись, по которой письмо
   проверяют).
3. Дождаться, пока Resend отметит домен проверенным.

Проверка: зарегистрировать тестовый аккаунт на почту в Gmail, письмо приходит во
«Входящие», а не в спам.

## 6. Google OAuth

Redirect URL в консоли Google должен совпадать с `GOOGLE_OAUTH_REDIRECT_URL`
символ в символ: `https://<домен>/api/auth/google/callback`. Расхождение в
хвостовом слэше или в `www` — это ошибка `redirect_uri_mismatch` и больше
ничего.

Проверка: вход через Google возвращает на сайт залогиненным.

## 7. Внешний cron — финализация попыток

Попытка турнира или скрамбла дня, начатая и не отправленная, висит в статусе
`started`, пока её не подметут. Метёт отдельная задача:

```bash
cd backend && python -m app.jobs.finalize
```

Она идемпотентна: обновляет только строки, которые всё ещё `started`, поэтому
запускать её можно как угодно часто и хоть параллельно. Планировщик — внешний
(cron-сервис Railway на том же образе, либо GitHub Actions по расписанию), не
внутри веб-процесса: внутрипроцессный планировщик умирает вместе с воркером и
дублируется вместе с ним.

Разумная частота — каждые 5 минут: борд не показывает висящие попытки дольше
пяти минут. Обоснование — `backend/README.md` § Scheduled finalize.

Проверка: начать попытку и не отправлять результат; через окно
(`TOURNAMENT_ATTEMPT_WINDOW_SECONDS`, по умолчанию 10 минут) плюс интервал cron
она становится `dnf` сама.

## 8. Бэкапы базы

Включить автоматические бэкапы Postgres в Railway. Отдельно — проверить
**восстановление**: бэкап, из которого никто ни разу не разворачивался, — это не
бэкап, а надежда. Разворачиваем копию во временную базу и смотрим, что таблицы
на месте.

## Смоук после деплоя

Прогнать в проде живьём, по порядку — каждый пункт трогает свой кусок:

- [ ] `/health` отвечает 200.
- [ ] Регистрация → письмо пришло во «Входящие» → ссылка подтверждает почту.
- [ ] Вход по паролю, перезагрузка страницы — сессия жива (cookie ставится).
- [ ] Вход через Google.
- [ ] Соло-сборка сохраняется и видна в профиле.
- [ ] Скрамбл дня и турнир: попытка стартует, результат записывается, борд обновляется.
- [ ] Дуэль по ссылке между двумя браузерами.
- [ ] Смена языка RU/EN не ломает ни один из экранов выше.
- [ ] Открыть сайт с телефона — показывается гейт «нужен компьютер», а не сломанный ритуал.

## Откат

Фронт: во Vercel вернуть предыдущий deployment (мгновенно).

API: в Railway откатиться на предыдущий образ. **Осторожно с миграциями** —
откат кода не откатывает схему. Если в выкатке была миграция, ломающая
совместимость со старым кодом, сначала `alembic downgrade -1`, и только потом
откат образа. Поэтому миграции, удаляющие или переименовывающие колонки, стоит
разбивать на две выкатки: сначала код, который умеет и так и так, потом схема.
