> Планировал: opus. Исполняет: sonnet-агент по этому файлу.
> Пользователь спит и недоступен — вопросов задавать некому, все решения уже приняты
> и записаны ниже вместе с причинами.

## 0. Что это за проект и что важно не сломать

Cubr — веб-платформа для спидкубинга, где судьёй выступает камера пользователя.
React+TS SPA (`frontend/`), FastAPI + async SQLAlchemy (`backend/`), Postgres.

Четыре факта, которые определяют всю конфигурацию:

1. **Компьютерное зрение работает в браузере.** Кадры с камеры на сервер не уходят
   вообще — это обещано пользователям в `/privacy`. Сервер не считает пиксели,
   поэтому одного ядра хватает.
2. **Камере нужен HTTPS.** `getUserMedia` работает только в защищённом контексте.
   Без сертификата сайт откроется, но весь ритуал сборки будет мёртв.
3. **Ровно одна реплика, ровно один воркер.** Комнаты дуэлей живут в памяти одного
   процесса (`backend/app/services/duel_manager.py`); `app/main.py` отказывается
   стартовать при `WEB_CONCURRENCY > 1`. Это не тюнинг, а требование корректности.
4. **Postgres наружу не смотрит.** Порт 5432 не публикуется в хост вообще, база
   доступна только внутри docker-сети.

## 2. Целевая архитектура

Всё на одной машине, три контейнера в одной docker-сети:

```
интернет :443 ──► Caddy ──┬─► статика фронта (/srv/cubr/www)
                          └─► /api/*  ──► api:8000 (FastAPI, 1 воркер)
                                              │
                                          db:5432 (Postgres 16, только внутри сети)
```

**Почему один origin, а не отдельный поддомен для API.** Cookie авторизации живёт
с `SameSite=lax`; при разных origin она просто не доедет, и вход перестанет
работать. Плюс WebSocket дуэлей проходит проверку Origin (`DUEL_ALLOWED_WS_ORIGINS`,
защита от CSWSH). Один origin снимает оба вопроса без единой настройки CORS.

**Почему Caddy, а не nginx.** Сертификат Let's Encrypt выпускается и продлевается
сам, без cron и certbot. Конфигурация — десять строк вместо ста.

### Фаза 1. Дозакрыть сервер

Выполняется под `root`. Порядок важен: старый путь отключается последним, уже
после проверки нового.

```bash
# firewall: наружу только SSH, HTTP, HTTPS
ufw default deny incoming
ufw default allow outgoing
ufw allow 22/tcp
ufw allow 80/tcp
ufw allow 443/tcp
ufw --force enable
```

Затем — и только после того, как `ssh deploy@135.106.181.244` подтверждён рабочим
(это уже проверено при планировании: вход, sudo и docker под `deploy` работают):

```bash
sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sed -i 's/^#\?PermitRootLogin.*/PermitRootLogin prohibit-password/' /etc/ssh/sshd_config
# Ubuntu 24.04 кладёт переопределения в /etc/ssh/sshd_config.d/*.conf — они
# перекрывают основной файл, поэтому проверить и там.
grep -rn "PasswordAuthentication\|PermitRootLogin" /etc/ssh/sshd_config.d/ || true
sshd -t && systemctl reload ssh
```

`PermitRootLogin prohibit-password`, а не `no`: вход root по ключу остаётся
работать (им пользуется этот деплой), запрещается только вход по паролю.

**Проверка:** `ssh deploy@…` работает; `sshd -t` молчит; `ufw status` показывает
три разрешённых порта.

### Фаза 2. Артефакты деплоя в репозитории

Ветка `feat/deploy-vps` от `main`. Коммиты атомарные, сообщения — нормальной
прозой на английском, как принято в проекте.

Создать:

**`deploy/docker-compose.yml`** — три сервиса.

- `db`: образ `postgres:16-alpine`, том `pgdata`, переменные `POSTGRES_USER=cubr`,
  `POSTGRES_DB=cubr`, `POSTGRES_PASSWORD` из `.env`. **Порты наружу не публиковать.**
  Healthcheck `pg_isready`. Под 2 ГБ памяти machine-wide: `shared_buffers=256MB`,
  `max_connections=50` — дефолтные 128 соединений на такой машине означают
  переподписку памяти.
- `api`: собирается из `../backend` (`build: context: ../backend`), `env_file: .env`,
  `depends_on: db (service_healthy)`, `restart: unless-stopped`. Порт **не**
  публиковать в хост — только внутрь сети.
- `caddy`: образ `caddy:2-alpine`, порты `80:80` и `443:443`, тома с `Caddyfile`,
  каталогом статики и `caddy_data` (там живут сертификаты — том обязателен,
  иначе при каждом перезапуске новый выпуск и упор в лимиты Let's Encrypt).

Сеть с фиксированной подсетью и **статическим IP для caddy** — он попадёт в
`TRUSTED_PROXIES`:

```yaml
networks:
  cubr:
    ipam:
      config:
        - subnet: 172.28.0.0/16
```

`caddy` получает `ipv4_address: 172.28.0.10`.

Почему статический IP: `app/main.py` отдаёт `ProxyHeadersMiddleware` список
доверенных адресов из `TRUSTED_PROXIES`, и по этому же IP считаются все
рейт-лимиты. Список слишком широкий — клиент подделает свой IP и обойдёт лимиты;
слишком узкий — весь сайт считается одним клиентом. Docker без фиксации выдаёт
контейнеру произвольный адрес из подсети, и после перезапуска список бы врал.

**`deploy/Caddyfile`**:

```
{$SITE_DOMAIN} {
    encode zstd gzip

    handle /api/* {
        uri strip_prefix /api
        reverse_proxy api:8000
    }

    handle {
        root * /srv/www
        try_files {path} /index.html
        file_server
    }
}
```

`try_files … /index.html` обязателен: это SPA с клиентским роутингом, без фолбэка
любой прямой заход на `/solo` или `/duel/join/<token>` вернёт 404.
`uri strip_prefix /api` нужен потому, что бэкенд слушает пути без префикса
(`/health`, `/solves`), а SPA ходит на `/api/...` (`frontend/src/api/client.ts`).
WebSocket через `reverse_proxy` проходит сам — Caddy пробрасывает Upgrade без
дополнительных директив.

**`deploy/.env.example`** — прод-версия списка из `backend/.env.example`, с
пустыми секретами и пометками. Реальный `.env` в репозиторий не попадает
(проверить `.gitignore`).

**`docs/deploy.md`** — переписать под этот способ вместо Railway. Сохранить
разделы «Смоук после деплоя» и «Откат», заменить платформенные шаги на:
сервер, compose, Caddy, cron, бэкапы. Явно записать: `backend/railway.json`
больше не является путём деплоя, но файл оставить — он документирует
ограничение `numReplicas: 1`.

**Проверка:** `docker compose -f deploy/docker-compose.yml config` разбирает файл
без ошибок.

### Фаза 3. Сборка фронта

Собирать **локально на ноутбуке**, не на сервере: `npm ci` + vite-сборка на
1 vCPU / 2 ГБ рискует упереться в память, а результат байт в байт тот же.

```bash
cd frontend && npm ci && npm run build
```

`prebuild` (`scripts/check-api-proxy.mjs`) на локальной сборке только предупреждает
про плейсхолдер в `vercel.json` — это ожидаемо и не мешает: Vercel мы не
используем, проксирование делает Caddy. `postbuild` проверяет бюджет входного
чанка в 320 кБ; если он не проходит — это настоящая регрессия, останавливаться.

Залить `frontend/dist/` на сервер в `/srv/cubr/www`:

```bash
rsync -az --delete frontend/dist/ deploy@135.106.181.244:/srv/cubr/www/
```

**Проверка:** на сервере `ls /srv/cubr/www/index.html` существует, размер
каталога сопоставим с локальным `dist`.

### Фаза 4. Поднять стек и накатить миграции

На сервере в `/srv/cubr` (владелец `deploy`) положить `docker-compose.yml`,
`Caddyfile` и `.env`.

Секреты сгенерировать **на сервере**, каждый своей командой:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(48))"
```

Нужны четыре разных: `SECRET`, `RESET_VERIFY_SECRET`, `SCRAMBLE_SIGN_SECRET`,
`DUEL_SIGN_SECRET`, плюс пароль Postgres. Приложение откажется стартовать, если в
значении встретится `change-me`, `placeholder` или `example`.

**Секреты никогда не попадают в репозиторий, в отчёт, в журнал и в чат.**
`.env` — права `600`, владелец `deploy`.

Значения, отличные от локальных:

| Переменная | Значение |
|---|---|
| `DATABASE_URL` | `postgresql+asyncpg://cubr:<пароль>@db:5432/cubr` |
| `APP_ENV` | `production` |
| `CORS_ORIGINS` | `https://cubr-game.ru` |
| `DUEL_ALLOWED_WS_ORIGINS` | `https://cubr-game.ru` |
| `FRONTEND_URL` | `https://cubr-game.ru` |
| `TRUSTED_PROXIES` | `172.28.0.10` |
| `WEB_CONCURRENCY` | `1` |
| `GOOGLE_OAUTH_REDIRECT_URL` | `https://cubr-game.ru/api/auth/google/callback` |

`DATABASE_URL` обязан начинаться с `postgresql+asyncpg://` — движок асинхронный,
с голой схемой `postgresql://` он не поднимется.

```bash
docker compose up -d db
docker compose run --rm api alembic upgrade head
docker compose up -d
```

Миграции 0001…0010 накатываются на пустую базу. Упала миграция — не поднимать
api, разбираться.

**Проверка:** `docker compose ps` — все три контейнера `healthy`/`running`;
`docker compose exec -T api python -c "import app.main"` не падает;
`curl -s localhost:8000/health` изнутри сети отдаёт 200 (внутри настоящий
`SELECT 1`, то есть это проверка и базы тоже).

### Фаза 5. Домен и HTTPS

К моменту исполнения A-запись `cubr-game.ru → 135.106.181.244` может ещё не
появиться: пользователь добавляет её вручную перед сном, а делегирование `.ru`
иногда тянется часами.

```bash
dig +short A cubr-game.ru
```

- **Отвечает нужным IP** → `SITE_DOMAIN=cubr-game.ru`, поднять Caddy, он сам
  возьмёт сертификат.
- **Пусто** → ждать, проверяя раз в 10 минут, не дольше двух часов суммарно.
- **Через два часа всё ещё пусто** → поднять на `135-106-181-244.sslip.io`
  (`sslip.io` резолвит IP из имени, Let's Encrypt такие имена подписывает).
  Сайт утром живой, переключение на настоящий домен — правка `SITE_DOMAIN`,
  `CORS_ORIGINS`, `DUEL_ALLOWED_WS_ORIGINS`, `FRONTEND_URL` и `docker compose up -d`.

При смене домена эти четыре переменные меняются **вместе** — рассогласование
даст рабочую страницу, на которой не работает ни вход, ни дуэли.

**Проверка:** `curl -sI https://<домен>/` отдаёт 200 и валидный сертификат;
`curl -s https://<домен>/api/health` отдаёт 200; прямой заход на
`https://<домен>/rules` отдаёт страницу, а не 404 (это и есть проверка SPA-фолбэка).

### Фаза 6. Cron и бэкапы

Финализация висящих попыток — идемпотентная задача, её можно запускать как угодно
часто:

```cron
*/5 * * * * cd /srv/cubr && /usr/bin/docker compose run --rm api python -m app.jobs.finalize >> /var/log/cubr-finalize.log 2>&1
```

Пять минут — потому что борд не должен показывать зависшую попытку дольше этого.

Ежедневный дамп базы в `/srv/cubr/backups`, хранить 14 дней:

```cron
30 4 * * * cd /srv/cubr && docker compose exec -T db pg_dump -U cubr cubr | gzip > backups/cubr-$(date +\%F).sql.gz && find backups -name 'cubr-*.sql.gz' -mtime +14 -delete
```

Ротация логов: `/etc/logrotate.d/cubr` на `/var/log/cubr-*.log`, иначе за месяц
логи съедят диск.

**Проверка:** запустить finalize руками — отрабатывает и печатает, сколько
попыток подмёл (на пустой базе ноль, это нормально); `pg_dump` создаёт непустой
архив; `gunzip -t` подтверждает целостность.

### Фаза 7. Смоук

По `docs/deploy.md`, всё что достижимо без камеры и без второго человека:

- [ ] `https://<домен>/` отдаёт лендинг.
- [ ] `/rules` и `/privacy` открываются прямой ссылкой.
- [ ] `/api/health` → 200.
- [ ] Регистрация нового пользователя через API → 201.
- [ ] Вход → приходит cookie с флагами `Secure`, `HttpOnly`, `SameSite=Lax`.
- [ ] `GET /api/users/me` с этой cookie → 200.
- [ ] `GET /api/scramble` → строка скрамбла и `scramble_token`.
- [ ] `POST /api/solves` с этим токеном → 201, сборка появляется в истории.
- [ ] `GET /api/daily/current` под аутентификацией → 200, аноним → 401.
- [ ] Рейт-лимит: 11 попыток входа подряд с одного IP → 429 (проверяет заодно,
      что `TRUSTED_PROXIES` настроен верно).
- [ ] Смена языка RU/EN на странице не ломает её.

Тестового пользователя после смоука удалить из базы, чтобы утром история была
чистой.

## 4. Границы: чего не делать ни при каких обстоятельствах

- **Не коммитить секреты.** Ни в репозиторий, ни в отчёт, ни в журнал.
- **Не публиковать порт Postgres** в хост.
- **Не поднимать `WEB_CONCURRENCY` выше 1** и не добавлять реплики.
- **Не трогать `main`** — вся работа в `feat/deploy-vps`.
- **Не менять код приложения** ради деплоя. Понадобилась правка кода — это
  находка для утреннего разбора, а не повод править на ходу. Исключение —
  конфигурационные файлы в `deploy/` и документация.
- **Не выпускать сертификат в цикле.** У Let's Encrypt лимит 5 выпусков на домен
  в неделю; упереться в него — значит оставить сайт без HTTPS до утра.
  Отладку вести на `--dry-run`-эквиваленте или на staging-эндпоинте Caddy.
- **Не удалять и не пересоздавать том `pgdata`** при отладке.
