# План: личная аналитика сборок («Коуч»), V3 роадмапа — frontend-only

Источник задачи: `.memory-bank/product-overview/roadmap.md` V3 «Личный коуч-аналитика»
(⭐⭐, 🟡). Честная рамка: настоящий разбор по фазам (крест→F2L→OLL→PLL) заблокирован
риском R1 (зрение по видео) и в этой фиче не появляется — ни выдуманных фаз, ни
утверждений вида «твой F2L медленный». Показываем только то, что реально можно
посчитать из уже загруженной истории сборок.

## 1. Что уже есть (прецеденты, переиспользуем приём)

- `frontend/src/profile/goals.ts` + `GoalCard.tsx` — цели sub-N из личного рекорда.
- `frontend/src/profile/average.ts` — текущий Ao5 из последних 5 попыток.
- `frontend/src/components/SolveProgressChart.tsx` — inline-SVG график, есть готовый
  `percentile()` (копируем паттерн, не импортируем — модули договорились оставаться
  независимыми, как правила Ao5 продублированы между `average.ts` и
  `backend/app/services/averages.py`).
- Все три читают проп `solves: SolveRead[]`, который `ProfilePage.tsx` грузит ОДИН раз
  через `listSolves(50, 0)` в компоненте `History`. Новых запросов/эндпоинтов не будет.

Ось честности из `.memory-bank`: `status` — `valid | dnf | rejected`. `rejected` — не
попытка (ритуал не соблюдён), `dnf` — попытка без числового результата (не «плохая
попытка», а бессмысленно как число). Это уже реализовано в `average.ts`
(currentAo5: `rejected` пропускается целиком, `dnf` занимает слот в окне, но без
времени) и в `goals.ts` (validTimes отбрасывает и `dnf`, и `rejected` — там речь только
о скорости). Наш модуль следует ЭТОЙ ЖЕ логике: числовые метрики (медиана, разброс,
рекорд/типичное, тренд скорости) считаются только по `status==="valid"` — DNF не
подставляется как «медленное время», это не-попытка для арифметики времени, а не
плохой результат. Доля DNF — отдельная метрика по попыткам `valid|dnf` (rejected
исключён и там, как в `daily/streak`).

## 2. Что показываем и почему

| Показываем | Почему честно | Почему полезно |
|---|---|---|
| Разброс (межквартильный размах валидных времён в окне) | Чистая статистика по факту загруженных времён, без модели/прогноза | «Рекорд без стабильности — везение» (текст задачи); показывает типичный диапазон, а не только пиковое время |
| Тренд (медиана последних N против предыдущих N) | Медиана, а не среднее — один выброс не переворачивает вывод; окно фиксировано и одинаково для обеих половин | Отвечает «стал ли я быстрее», не выдумывая процент на пяти сборках |
| Доля DNF + её динамика (последние N против предыдущих N попыток) | Считается по попыткам (valid+dnf), как ритуал в `daily/streak`, а не выдумывается | Растущая частота срывов — реальный сигнал дисциплины, не связан со скоростью |
| Лучшая/типичная/худшая сборка окна, отрыв рекорда от типичного | Факты по загруженному окну + отношение best/median | «Большой отрыв — рекорд случайный» (текст задачи) |
| Время суток / день недели | — | **Сознательно НЕ показываем.** Окно ≤50 сборок при 24 часах/7 днях недели даёт в среднем ~2 сборки на час и ~7 на день недели — меньше нашего же порога осмысленности `MIN_SAMPLE=5` почти в каждой корзине. Показать это значило бы либо нарушить наш собственный порог, либо обмануть агрегацией по столь скудным корзинам. Как только появится вменяемый источник данных (больше истории на клиенте или бэкенд-агрегация), это можно добавить отдельным проходом. |

## 3. Порог осмысленности (обязательное требование)

`MIN_SAMPLE = 5` — минимальный размер ОДНОГО окна (валидных сборок для скоростных
метрик, попыток valid+dnf для доли DNF) прежде чем модуль вообще произносит числовой
вывод. Обоснование:
- Уже используется в проекте как порог «достаточно, чтобы о чём-то судить»:
  `AVERAGE_SIZE` (Ao5) и `STREAK_TARGET` в `goals.ts` — оба равны 5. Не изобретаем
  новое число, а used same acuity level, которым уже доверяет остальной продукт.
- Пример из самой задачи — «на пяти сборках "стал быстрее на 12%" — шум» — не про
  единичное окно, а про ТРЕНД: тренд сравнивает ДВА окна по `MIN_SAMPLE`, значит
  минимум **10** валидных сборок нужно, чтобы вообще показать тренд. При 5 валидных
  сборках тренда не будет — ровно тот случай, который в задаче назван шумом, закрыт
  структурно (не хватает данных даже на одно сравнение), а не эвристикой процента.
- Разброс/типичное/рекорд-vs-типичное открываются раньше (на `MIN_SAMPLE=5`), потому
  что это факты по уже случившимся сборкам (не прогноз и не сравнение периодов) —
  ровно тот здравый смысл, по которому Ao5 в проекте уже официально существует на пяти
  попытках.
- Доля DNF открывается на `MIN_SAMPLE` попытках (valid+dnf), её тренд — на `2×MIN_SAMPLE`
  попытках, той же логикой, что и скоростной тренд.

Пока порог не достигнут, карточка честно говорит «нужно ещё N сборок», не показывая
никаких чисел — так же, как `GoalCard` говорит «появится после первой засчитанной
сборки» вместо нуля/прочерка.

## 6. `CoachSummary` — форма данных

```ts
export const MIN_SAMPLE = 5;

export interface CoachSummary {
  validCount: number;    // валидных сборок в окне
  attemptCount: number;  // valid+dnf в окне (rejected исключён)

  medianMs: number | null;   // порог MIN_SAMPLE валидных
  p25Ms: number | null;
  p75Ms: number | null;

  bestMs: number | null;
  worstMs: number | null;
  gapRatio: number | null;   // medianMs / bestMs, >=1
  likelyLucky: boolean;      // gapRatio >= SPIKE_RATIO (1.3)

  trendRecentMedianMs: number | null; // порог 2*MIN_SAMPLE валидных
  trendPriorMedianMs: number | null;
  trendDeltaPct: number | null;       // отрицательное = стало быстрее

  dnfRate: number | null;             // порог MIN_SAMPLE попыток, по ВСЕМУ окну попыток
  dnfTrendRecentRate: number | null;  // порог 2*MIN_SAMPLE попыток
  dnfTrendPriorRate: number | null;
  dnfTrendDeltaPts: number | null;    // в процентных пунктах
}
```

`SPIKE_RATIO = 1.3` — рекорд минимум на 30% быстрее типичного (медианы) окна
считается «возможно, повезло». Число не выдаётся за статистическую значимость —
UI-текст говорит «возможно», не «наверняка». Обоснование величины: 30% — это уже
далеко за пределами обычного дневного разброса кубера (см. `spreadRatio`, обычно
десятки процентов, не первые единицы), но не настолько строгое, чтобы никогда не
сработать. Порог — эвристика, оформлена как одна именованная константа для лёгкой
правки, если реальные данные покажут другое.

Ao5-подобный выбор: «типичное» = медиана валидных времён окна (устойчива к одному
выбросу), не среднее — тест «выброс не ломает вывод» именно на этом и держится.

## 7. Test plan

`frontend/tests/profile/coach.test.ts` (чистая логика `buildCoachSummary`):
1. Пустая история (`[]`) → все поля `null`/`0`, `validCount===0`, `attemptCount===0`.
2. Одна валидная сборка → всё ещё `null` (`MIN_SAMPLE=5` не достигнут), `validCount===1`.
3. Все DNF (например 6 штук) → `validCount===0` (метрики скорости `null`),
   `attemptCount===6` (доля DNF СЧИТАЕТСЯ — попытки были), `dnfRate===1`.
4. Ровно на границе порога: 5 валидных сборок → `medianMs`/`p25Ms`/`p75Ms`/`bestMs`/
   `worstMs`/`gapRatio` не `null`. `trendRecentMedianMs` всё ещё `null` (нужно 10).
5. На единицу ниже границы: 4 валидные сборки → всё ещё `null` для
   разброса/типичного/рекорда. `attemptCount` независимо — если валидных 4, а DNF
   добавляет попытки до `MIN_SAMPLE`, `dnfRate` уже считается (проверяет, что пороги
   валидных сборок и попыток независимы друг от друга).
6. Граница тренда: 10 валидных сборок → тренд считается; 9 валидных → `trendDeltaPct`
   всё ещё `null`.
7. Граница DNF-тренда: аналогично на `attemptCount` 10 и 9 (valid+dnf).
8. Выброс не ломает вывод: 10 «обычных» валидных времён с чёткой скоростной тенденцией
   (первые 5 заметно быстрее вторых 5) + один гигантский выброс, вставленный в любую из
   половин — направление тренда (`trendDeltaPct` знак) не меняется, `bestMs`/`worstMs`
   корректно отражают реальные крайние значения (выброс обязан быть виден как `worstMs`,
   это не баг — баг был бы, если бы он сломал ТРЕНД).
9. DNF не считается «медленной сборкой»: сборки `[valid 20s, dnf, valid 21s, valid 19s,
   valid 22s, valid 20s]` → `dnf` не входит ни в `medianMs`, ни в `bestMs`/`worstMs`, ни
   в `p25/p75` (эти метрики считаются только по 5 валидным временам, `dnf`-строка
   игнорируется арифметикой времени, но `attemptCount` её учитывает).
10. `rejected` — тоже не-попытка: сборки со статусом `rejected` не входят ни в
    `validCount`, ни в `attemptCount`, ни в `dnfRate` (проверка на реальном крае из
    задания).
11. Детерминированность: один и тот же вход, вызванный дважды (в т.ч. с переиспользуемым
    массивом — проверяем, что `buildCoachSummary` не мутирует входной `solves`) → строго
    одинаковый результат (`toEqual`).
12. `likelyLucky`: рекорд намного быстрее типичного (`gapRatio >= 1.3`) → `true`;
    рекорд близко к типичному → `false`.

`frontend/tests/profile/CoachCard.test.tsx` (рендер):
1. Пустая история → текст «нужно ещё сборок» (без чисел, без deprecated «—»), ссылки на
   соло нет (это уже покрыто `EmptyCard` в `SolveProgressChart`, здесь просто честный
   текст, не дублируем CTA).
2. Ровно `MIN_SAMPLE` валидных сборок → показаны разброс/типичное/рекорд, тренд-блок
   говорит «нужно ещё N сборок для тренда» (не молчит и не показывает `null` как текст).
3. `2×MIN_SAMPLE` валидных сборок с ясным трендом → показана формулировка
   «быстрее/медленнее на N%» с правильным знаком направления.
4. Все DNF → карточка показывает долю DNF (100%), но НЕ показывает
   разброс/типичное/рекорд (эти блоки — свой «нужно ещё» текст, т.к. `validCount===0`).
5. `likelyLucky` → в тексте видна отметка «возможно, повезло» (или её отсутствие, когда
   `false`).

## 8. Бюджет бандла

Новый код — чистые функции + одна презентационная карточка, без новых зависимостей,
без камеры/MediaPipe. Ожидаемый прирост входного чанка — низкие единицы КБ (текстовые
строки в основном идут через `en.ts`, который уже в бандле). Запас на момент старта —
8 КБ (312/320). После сборки прогоняем `npm run build` (включает `postbuild` —
`scripts/check-bundle.mjs`) и фиксируем реальное число в отчёте. Если бюджет всё же
не влезает — не поднимаем порог, а не рассматриваем: карточка не тянет ленивый роут
(она часть уже нелёгкого `/profile`), поэтому единственный рычаг — экономить текст/код;
поднятие бюджета — крайний случай, требует явного решения, не мой дефолт.

## 9. Риски / что сознательно НЕ делаем

- Не трогаем бэкенд, не добавляем эндпоинтов, не меняем `SolveRead`.
- Не делаем разбор по фазам (крест/F2L/OLL/PLL) — заблокировано R1, будет отдельной
  фичей после зрения по видео.
- Не показываем время суток/день недели (см. §2, таблица, последняя строка) —
  сознательный отказ, не забытая часть.
- Не добавляем настроек/переключателей окна — окно то же (≤50), что уже грузит
  `ProfilePage`, без нового UI для выбора периода (не входит в узкий скоуп задачи).
