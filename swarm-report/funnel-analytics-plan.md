# План — Этап 6: минимальная аналитика воронки

Чеклист Этапа 6: «регистрация → первая сборка → первая дуэль».

## Решение: считаем ПО УЖЕ ЗАПИСАННЫМ данным, ничего не трекаем

Никакого стороннего трекера, ни одного нового события, ни таблицы, ни миграции.
Все ступени воронки уже выводятся из существующих строк:

| Ступень | Источник |
| --- | --- |
| зарегистрировался | `users` |
| подтвердил почту | `users.is_verified` |
| завёл кубик | `cubes.user_id` distinct |
| сделал сборку | `solves.user_id` distinct |
| прошёл челлендж недели | `tournament_attempts.user_id` distinct |
| прошёл скрамбл дня | `daily_attempts.user_id` distinct |
| сыграл дуэль | `duel_participants.user_id` distinct |

Почему так, а не события/GA: (а) П10 — на публичный лендинг мы написали, что не следим;
класть внешний трекер сразу после этого нечестно; (б) воронка на 3–5 закрытых тестерах
не требует событийного конвейера; (в) ноль новых зависимостей и схем — откатывается удалением
одного роутера.

**Ограничение честно фиксируем:** это воронка *состояний*, а не *событий*. «Дошёл до
экрана и бросил» она не покажет — только «сделал / не сделал». Событийный поток появится
вместе с честностным кирпичом (там таймстампы клиента и так нужны), не раньше.

## Эндпоинт

`GET /admin/funnel`, **только суперюзер** (`fastapi_users.current_user(active=True,
superuser=True)`): аноним 401, обычный юзер 403. Отдаёт ТОЛЬКО числа — ни email, ни
никнеймов, ни id, ни IP. Плюс окна: `signups_7d` / `signups_30d` и «активные»
(сделали хоть что-то) за те же окна, чтобы конверсию можно было мерить на свежей когорте.

Схема `FunnelRead`: `users_total`, `users_verified`, `users_with_cube`,
`users_with_solve`, `users_with_tournament`, `users_with_daily`, `users_with_duel`,
`solves_total`, `duels_finished`, `signups_7d`, `signups_30d`, `active_7d`, `generated_at`.
