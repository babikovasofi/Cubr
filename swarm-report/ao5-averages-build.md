# Отчёт — Ao5: оживление мёртвой колонки `best_ao5_ms`

Найдено при обходе профиля: колонка `users.best_ao5_ms` приехала ещё на Этапе 2,
в схему и в UI попала, но **писать в неё было некому** — карточка «Лучший Ao5»
показывала «—» всегда и у всех. Это сеттер + текущее среднее в профиле.

## Что сделано

| Файл | Что |
| --- | --- |
| `backend/app/services/averages.py` (новый) | Чистая `ao5()` по правилам WCA + `current_ao5()` (окно последних пяти попыток). |
| `backend/app/routers/solves.py` | После записи сборки — пересчёт скользящего Ao5 и обновление рекорда (best-effort, как бейджи). |
| `frontend/src/profile/average.ts` (новый) | Те же правила для «текущего Ao5» из уже загруженной истории. |
| `frontend/src/pages/ProfilePage.tsx` | Строка «Текущий Ao5 (последние 5 попыток)». |

## Правила (как их ждут куберы)

- Ao5 отбрасывает лучшую И худшую попытку, среднее — по трём оставшимся.
- **Одна DNF не портит среднее:** DNF «медленнее любого времени», то есть это и
  есть отброшенная худшая. Две и больше DNF → среднее само становится DNF.
- `rejected` — **не** медленная попытка, а не-попытка (ритуал не соблюдён):
  пропускается целиком, не считается DNF-ом.
- Окно — пять последних попыток по `created_at` (скользящее), потому что понятия
  «сессия» в Cubr нет.
- Рекорд обновляется только при улучшении, как `best_single_ms`.

## Решения

- **Пересчёт после `flush()`**: новая сборка должна попасть в собственное окно.
  Ошибка расчёта не роняет запись сборки (try/except, тот же приём, что у
  бейджей) — потерять сборку из-за арифметики недопустимо.
- **Правила продублированы на фронте** — узко и осознанно: ради одной строки
  «сейчас» не заводить эндпоинт. Обе стороны покрыты тестами на ОДНИХ И ТЕХ ЖЕ
  примерах.
- **Тесты порядка идут мимо API.** sqlite хранит `created_at` с точностью до
  секунды, пять сборок подряд ложатся в одну метку и «последние пять» становятся
  недетерминированными. Сценарии, где важен порядок, вставляют строки напрямую с
  явными `created_at`; в проде (Postgres, микросекунды) проблемы нет.
